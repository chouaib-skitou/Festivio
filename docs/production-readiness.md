# Production readiness

This document records the production-readiness baseline introduced by PR #44.

## Runtime

- Environment validation fails fast before the server accepts traffic.
- Database connectivity is separated from Express app construction.
- `/health` exposes liveness and `/ready` includes MongoDB readiness.
- SIGTERM/SIGINT trigger bounded graceful shutdown.
- Backend and frontend production containers run as non-root users.

## Security

- Explicit credentials-aware CORS origins.
- Short-lived in-memory access tokens and rotating HttpOnly refresh cookies.
- Backend RBAC and event/task ownership enforcement.
- Privileged roles blocked from public registration.
- Hashed, expiring password-reset tokens and non-enumerating reset requests.
- API/auth rate limiting and constrained image uploads.
- Runtime `.env` files and database dump fixtures are not tracked.

## Local development

`docker compose up --build` starts React/Nginx, Express, MongoDB and Mailpit. A synthetic local seed is available with `npm run seed:demo` inside the backend container.

## Delivery

CI validates repository integrity, backend quality, frontend build/tests and the complete Compose stack. CodeQL and Dependabot provide security/dependency automation. semantic-release creates tags and GitHub Releases from `master`, and GitHub Releases publish frontend/backend images to GHCR.

## Version policy

The root, backend and frontend version must match. `npm run version:check` and CI enforce this invariant.

## Dependency lockfiles

The historical repository did not contain npm lockfiles. CI currently uses `npm install` for compatibility with that baseline. Adding generated lockfiles and migrating install steps to `npm ci` should be done as a dedicated dependency-reproducibility follow-up so lockfiles are generated by npm rather than hand-authored.
